## 1. Kernel already tells dyld "no TPRO"  [VERIFIED]

dyld decides hardware TPRO only from the apple[] string `dyld_hw_tpro`:
  /usr/lib/dyld VA 0x7b9fc..0x7ba14 (lsl::MemoryManager ctor):
    adrp/add x1 -> "dyld_hw_tpro" (0x96df0); bl 0x884c (apple[] lookup)
    cbz x0, skip; mov w8,#1; strb w8,[x20,#0x21]
  Every TPRO write-window (msr s3_6_c15_c1_5) is behind `ldrb [x,#0x21]==1`
  and then commpage byte 0xFFFFFC10C ((v & 0xfe) == 2), else `brk #1`.
- Kernel image has no "dyld_hw_tpro" string (strings -a Image.ipados).
- Kernel vm_map_tpro / vm_map_set_tpro / pmap_set_tpro are 4-byte stubs.
- Commpage at runtime (gdb at exception_triage):
    _commpage_ro_data_kva+0x100: 00..00   [0x10c]=0x0
    user 0xfffffc100:            00..00
So dyld runs its non-TPRO (mprotect) path. Nothing to add in the kernel.

## 3. Real wall: libdispatch "Missing Kevent WORKQ support"  [VERIFIED]

  EXC_TRIAGE exc=1 code0=0x1 code1=0x4000001e esr=0x92000006
  OS_REASON ns=2 code=0xb
PC unslid 0x1bd93f264 (libdispatch +0x39264) `ldr w8,[x0]`, x0=0x4000001e.
The caller (libdispatch +0x13fd8) did `bl 0x1bd93f188` = DISPATCH_CLIENT_CRASH
stub: msg "BUG IN LIBDISPATCH: Missing Kevent WORKQ support", code=w0, then
`brk #1`. --nop-brk1 NOPed that brk, so execution fell through several
crash stubs into the next function and faulted on the crash code as a pointer.
The SIGSEGV is a masked deliberate crash, not a memory-mapping bug.

0x4000001e is the mask that patch_fullroot_pthread_features.py forces. It
has no WORKQ_FEATURE_KEVENT (0x40) / WORKLOOP (0x80).

Kernel side:
  bsdthread_register -> pthread_functions (0xfffffe000756a800, version 1)
  -> +0xe0 = 0xfffffe000756abfc, returns 0x2d (ENOTSUP) for launchd.
That table is the historical aux_text.S stand-in that is still built into
qemu/Image (round 0014). Every workq/bsdthread entry is ENOTSUP or ret.
There is no pthread.kext in this kernel (only the xnu side:
_bsdthread_register, _workq_open, _bsdthread_ctl, _pthread_kext_register).
